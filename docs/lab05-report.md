# Звіт до лабораторної роботи 5

**Тема:** сервісний шар: інтерфейси, два сховища, ручний DI.
**Проєкт:** CrossApp. **Домен:** склад (Warehouse).

## 1. Мета, сутність та інтерфейс

Мета роботи — відокремити бізнес-операції від зберігання даних. Головна сутність Goods описує товар, його Id, SKU, назву, одиницю вимірювання, залишок і примітку. Вона перевіряє інваріанти та змінює залишок методами RegisterArrival і Issue. Сервіс CatalogService знаходить потрібний товар, викликає доменний метод і передає змінену сутність сховищу.

Контракт ICatalogStore містить рівно п'ять методів:

| Метод | Чому потрібен |
| --- | --- |
| IReadOnlyList<Goods> List() | Показати каталог і отримати дані для пошуку |
| Goods? GetById(string id) | Знайти конкретний товар; null означає відсутність |
| void Add(Goods item) | Додати товар з новим Id |
| void Update(Goods item) | Зберегти залишок після приходу або видачі |
| bool Remove(string id) | Видалити товар і повідомити, чи був він у сховищі |

Повторний Id та оновлення відсутнього Id викликають InvalidOperationException. Порожні аргументи відхиляються ArgumentException/ArgumentNullException. Ключі порівнюються без урахування регістру. Списки лише для читання; сутності передаються як незалежні копії, тому сторонній код не обходить Update.

## 2. Реалізації й формат зберігання

InMemoryCatalogStore зберігає сутності в Dictionary. Конструктор приймає необов'язкову послідовність початкових товарів. Для демонстрації SampleData.Goods() повертає 18 записів. Після завершення процесу внесені зміни зникають; новий процес отримує новий набір початкових даних.

FileCatalogStore читає файл під час першого звернення й кешує дані. Кожна успішна зміна Add/Update/Remove записує новий JSON. Відсутній файл означає порожнє сховище. На диск серіалізується масив GoodsDto з полями Id, Sku, Name, Unit, Quantity, Note. Під час читання Goods.FromDto перевіряє доменні інваріанти. Пошкоджений файл не обнуляється. Запис через тимчасовий файл захищає оригінал від частково записаного JSON; кеш оновлюється після успішної заміни.

Шлях за замовчуванням: AppContext.BaseDirectory/data/catalog.json. У Debug/net10.0 це src/Cli/bin/Debug/net10.0/data/catalog.json. Параметри `--file --path data/catalog.json` вибирають файл у папці data кореня проєкту. Для автоматичних перевірок використовувався окремий тимчасовий каталог, щоб не змінювати демонстраційні дані користувача.

## 3. Схема залежностей

```text
Cli → CatalogService → ICatalogStore ← InMemoryCatalogStore
                                    ← FileCatalogStore
                                    ← CachingCatalogStore → ICatalogStore
```

Стрілка від реалізації до ICatalogStore позначає реалізацію інтерфейсу. CatalogService залежить від контракту через конструктор. Він не знає конкретних класів зберігання. Composition root у Cli створює конкретні об'єкти. Залежності передаються вручну, без Microsoft.Extensions.DependencyInjection.

## 4. Composition root та фактичні результати

Фрагмент основного варіанта (7 рядків, без навколишньої гілки if):

```csharp
StoreOptions options = StoreOptions.Parse(args);
ICatalogStore store = options.UseFile
    ? new FileCatalogStore(options.DataPath)
    : new InMemoryCatalogStore(SampleData.Goods());
if (options.UseCache)
    store = new CachingCatalogStore(store);
var service = new CatalogService(store);
```

Нижче — вибрані рядки фактичних запусків .NET 10. Повні списки та довгий шлях тимчасового файла пропущено; ідентифікатори збережено з реального виводу.

## 5. Перехід на базу даних

Для переходу на БД необхідно реалізувати ICatalogStore, наприклад класом DbCatalogStore, і вибрати його в composition root або StoreFactory. Методи Add, Receive, Issue та інші операції CatalogService залишаються незмінними, поки зберігається контракт. Домен Goods також не залежить від способу зберігання. Для роботи кількох користувачів потрібні транзакції й контроль конкурентних змін; поточні синхронні локальні сховища розраховані на один процес/потік.

## 6. Додаткові завдання

1. **CachingCatalogStore** реалізує ICatalogStore й приймає інше сховище в конструкторі. Він кешує перше читання, передає зміни внутрішньому сховищу й скидає кеш після успішного запису. CountingStore у тестах підтвердив один List для кількох повторних читань і нове читання після зміни. Декоратор не відстежує зміни, виконані в обхід нього.
2. **Search(Func<Goods, bool>)** отримує предикат, виконує Where та повертає захищений список. У CLI показано пошук товарів у метрах із залишком від 60. Null-предикат відхиляється.
3. **StoreFactory.Create(args)** переносить вибір реалізації в окремий клас у Cli. Прапорець --factory вмикає цей варіант, без нього створення лишається в Program.cs. Фабрика дозволяє окремо перевіряти створення залежностей; у невеликому застосунку прямий варіант коротший. Обидва використовують один сервіс; фабрика є альтернативною частиною composition root, а не DI-контейнером.

## 7. Перевірка та висновок

Збірка CrossApp.slnx успішна для net8.0 і net10.0: 0 попереджень, 0 помилок. На встановленому .NET 10 виконано 45 нових перевірок ServiceChecks і 56 перевірок DomainChecks без помилок. Окремо пройшли 17 перевірок запуску CLI, включно з Git Bash, накопиченням JSON, читанням без змін, усіма комбінаціями фабрики/кешу та помилками введення. Runtime .NET 8 не встановлений, тому для цієї платформи перевірено компіляцію, але не запуск.

Тести перевіряють спільний контракт у чотирьох конфігураціях, незалежність копій, CRUD, пошук, інваріанти, недопустимий JSON, відсутність часткового кешу після помилок, збереження стану при невдалому записі й оновлення кешу. На Windows додатково перевірено заблокований файл. За пунктом самоперевірки окремо зібрано Core без FileCatalogStore для net8.0 і net10.0: обидві збірки успішні, що підтверджує незалежність сервісу від файлової реалізації.

Результат: один сервіс працює з двома взаємозамінними сховищами; конкретні залежності вибираються поза сервісом. Реалізовано всі три додаткові завдання. Команди для захисту наведено в lab05-defense.md, для окремого коміту lab05 — у lab05-commit.md.
