# Звіт до лабораторної роботи 6

**Тема:** доменні події, делегати Action/Func, лямбди.
**Предметна область:** склад будівельних матеріалів, Warehouse, сутність Goods.
**Мета:** сповіщати зовнішній код про успішні зміни стану без залежності бізнес-логіки від конкретного способу оброблення повідомлень.

## 1. Події в моєму домені

Added означає додавання товару, Received — прихід на склад, Issued — видачу, Removed — вилучення запису з каталогу. Ці дії змінюють стан каталогу й потребують повідомлення зовнішніх компонентів. Find/All/FindAll лише читають дані, тому подій не формують. Якщо порушено інваріант або запис сховища не вдався, події немає. Повторне видалення відсутнього товару повертає false без сповіщення.

CatalogChangedEventArgs успадковує EventArgs та має get-only властивості Id, Kind, Delta, QuantityAfter, At. At містить дату, час і UTC offset. Delta позитивна при приході, негативна при видачі. Для Removed Delta дорівнює мінус залишку видаленого товару, QuantityAfter=0; це означає відсутність запису, а не окрему фізичну видачу.

## 2. Оголошення та підняття події

```csharp
public event EventHandler<CatalogChangedEventArgs>? Changed;
private void OnChanged(Goods item, CatalogChangeKind kind, int delta)
{
    var change = new CatalogChangedEventArgs(item.Id, kind, delta,
        kind == CatalogChangeKind.Removed ? 0 : item.Quantity);
    Changed?.Invoke(this, change);
    notificationSink?.Notify(change);
}
```

OnChanged викликається після успішного _store.Add/_store.Update/_store.Remove. Sender — сам сервіс. Без підписників ?.Invoke нічого не робить. Необов'язковий notificationSink використовується додатковим сценарієм ручного DI. Якщо підключити обидва механізми, Changed викликається перед Notify з тими самими аргументами.

## 3. Підписники тепер і в майбутніх роботах

У CLI підписано локальний метод OnCatalogChanged, який виводить подію та дописує app.log, і лямбду counter, яка збільшує захоплений лічильник changes. Порядок демонструють рядки [1] та [2]. Лямбду збережено у змінній для коректної відписки. Після -= OnCatalogChanged перший одержувач мовчить, другий продовжує рахувати. Після -= counter дані змінюються без сповіщень. Finally знімає обидві підписки і при винятку.

За планом курсу в роботі 10 підписником може бути логер Api, а в роботі 12 — компонент Blazor для оновлення таблиці. Ці компоненти не реалізовувалися наперед: механізм подій уже дозволяє підключити їх ззовні без нового способу виводу в Core.

## 5. Подія та прямий виклик логера: два наслідки

Якби CatalogService безпосередньо викликав конкретний файловий логер чи Console.WriteLine, додавання API або інтерфейсу Blazor змушувало б редагувати бізнес-код. Подія дозволяє зовнішньому клієнту самостійно підписатися. Другий наслідок — тестованість: зараз перевірка підписується на Changed і порівнює аргументи без читання консолі чи журналу. Прямий IO у сервісі вимагав би тестувати ці зовнішні ресурси разом із бізнес-операціями.

Подія не гарантує доставку всім слухачам при довільних винятках: стандартний EventHandler синхронний, і необроблений виняток зупинить наступних. Тому очікувані помилки запису обробляє FileSink всередині Notify; CLI бачить FailureCount, повідомляє про збій і повертає 1. Успішна бізнес-зміна не відкочується через відмову журналу.

## 6. Додаткове завдання 1: INotificationSink

Оголошено INotificationSink у Core/Abstractions; ConsoleSink та FileSink реалізовані в Cli/Notifications. Cli створює кожен конкретний sink і передає його через другий параметр конструктора CatalogService. Для наочного порівняння створюються два окремі сервіси без Changed-підписників; кожен виконує чотири зміни. FileSink записує logs/sink.log, відокремлений від app.log.

Інтерфейс у конструкторі робить одержувача явною залежністю, його легко замінити тестовим об'єктом. Подія дозволяє мати багато незалежних підписників і динамічно керувати ними через += / -=. Sink залишається визначеним при створенні сервісу; event працює і з нульовою кількістю слухачів. Обидва підходи не вимагають конкретного IO-класу в Core. У демонстрації вони не застосовуються двічі до одного журналу, тому немає дублювання.

## 7. Додаткове завдання 2: Action<string>

GoodsCsvImporter.Load приймає необов'язковий Action<string> onSkipped. У гілці ParseFailed помилка спочатку додається до ImportResult.Errors, а потім передається callback. Лямбда в Cli друкує її та змінює skipped. Файл data/lab06.csv містить три коректні записи й три пошкоджені рядки; результат — 3 DTO, 3 помилки, 3 виклики Action з фізичними номерами 5, 6, 7. Пропущені коментарі, порожні рядки та заголовок не вважаються помилками. Старий виклик Load(path) без callback лишається працездатним.

FindAll(Func<Goods, bool>) використовує предикат для повернення результату пошуку; Action лише повідомляє без результату. Callback імпорту синхронний: необроблений виняток callback перериває імпорт, тому зовнішній код має обробляти ризиковані дії у своєму callback.
