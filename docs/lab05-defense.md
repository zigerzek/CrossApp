# Захист лабораторної роботи 5 — CrossApp / Warehouse

## Що сказати на початку

«У п'ятій лабораторній я відокремив операції складу від способу зберігання даних. Товар описує клас Goods. CatalogService додає товар, оформлює прихід і видачу. Сервіс працює через ICatalogStore, тому однаково використовує пам'ять або JSON-файл. Конкретне сховище я створюю в Cli й передаю сервісу через конструктор. Це ручне впровадження залежностей».

## Які файли показувати

1. `src/Core/Abstractions/ICatalogStore.cs` — контракт із п'яти методів:
   - `List()` — усі товари;
   - `GetById(id)` — один товар або `null`;
   - `Add(item)` — додавання, дубль Id заборонений;
   - `Update(item)` — збереження зміненого товару, відсутній Id заборонений;
   - `Remove(id)` — видалення, `false`, якщо товару немає.
2. `src/Core/Services/CatalogService.cs` — конструктор приймає **ICatalogStore**. У `Receive` видно три дії: знайти товар, викликати його доменний метод, зберегти через Update. `Issue` працює аналогічно.
3. `src/Core/Storage/InMemoryCatalogStore.cs` — Dictionary, початкові дані через конструктор. Id порівнюються без урахування регістру.
4. `src/Core/Storage/FileCatalogStore.cs` — перше звернення читає JSON; Add/Update/Remove записують зміни. На диск ідуть GoodsDto; FromDto перевіряє доменні правила під час відновлення.
5. `src/Cli/Program.cs` — тернарний вибір сховища і `new CatalogService(store)`.
6. Додаткові: `CachingCatalogStore.cs`, метод `CatalogService.Search`, `src/Cli/Composition/StoreFactory.cs`.

## Команди в Git Bash: основна частина

```bash
cd /c/dev/CrossApp
dotnet build CrossApp.slnx

# 1. Пам'ять: початкових товарів 18, після сценарію 19.
dotnet run --project src/Cli -f net10.0 --no-build

# 2. Новий процес: знову 18 початкових, доданого DEMO-005 немає.
dotnet run --project src/Cli -f net10.0 --no-build -- --list-only

# 3. JSON у папці data кореня проєкту. Цей самий шлях використовуємо далі.
dotnet run --project src/Cli -f net10.0 --no-build -- --file --path data/catalog.json
cat data/catalog.json

# 4. Повторний запуск: попередні товари залишилися, додається ще один.
dotnet run --project src/Cli -f net10.0 --no-build -- --file --path data/catalog.json

# 5. Лише читання, без додавання нового товару.
dotnet run --project src/Cli -f net10.0 --no-build -- --file --path data/catalog.json --list-only
echo $?
```

Файловий режим із новим файлом починає з 0 товарів, після першого сценарію — 1, після другого — 2. Якщо файл уже існує, відлік починається з його поточної кількості. Видаляти дані перед захистом не потрібно.

**Без `--path`** шлях відповідає прикладу методички: `AppContext.BaseDirectory/data/catalog.json`. Для Debug/net10.0 це `src/Cli/bin/Debug/net10.0/data/catalog.json`. CLI завжди друкує повний шлях. `--path data/catalog.json` явно вибирає файл у корені проєкту; не плутайте ці два файли.

У кожному звичайному запуску вже є сценарії помилок: повторний Id, прихід для відсутнього Id, видача понад залишок. Вони очікувані й перехоплені. Залишок нового товару: **50 → 75 → 65**, після відмов — **65**. Тимчасовий товар видаляється, тому кожен запуск залишає лише один новий демонстраційний товар. Повторні SKU допустимі: контракт вимагає унікальність Id.

Код `0` означає успішну демонстрацію, включно з очікуваними відмовами. Приклад помилки самого запуску:

```bash
dotnet run --project src/Cli -f net10.0 --no-build -- --unknown
echo $?
```

Тут буде зрозуміле повідомлення та код `1`, без stack trace. `echo $?` виконуйте одразу після потрібної команди.

`-f net10.0` вибирає одну з двох цільових платформ; `--no-build` запускає вже зібраний код. Після редагування спочатку повторіть build. Після `--` ідуть аргументи саме нашої програми.

## Усі три додаткові завдання

### 1. Декоратор кешування

«CachingCatalogStore теж реалізує ICatalogStore, але всередині має інше сховище. Перший List або GetById читає його список. Наступні читання використовують власний кеш. Успішні Add, Update та Remove скидають кеш, щоб наступне читання побачило зміни».

```bash
dotnet run --project src/Cli -f net10.0 --no-build -- --cache
dotnet run --project src/Cli -f net10.0 --no-build -- --file --path data/catalog.json --cache
```

У тесті `Decorator caches List/GetById and invalidates after each mutation` обгортка CountingStore рахує реальні виклики: кілька читань декоратора спричиняють один List внутрішнього сховища; після запису відбувається нове читання. Сам текст CLI не є вимірюванням кешу — доказ дає цей тест.

Файлове сховище вже має власний кеш диска. Декоратор показує окремий прийом розширення поведінки та може обгорнути будь-яке ICatalogStore. Для зовнішніх змін іншою програмою автоматичного оновлення немає: створюється новий екземпляр/процес.

### 2. Пошук із Func

```csharp
public IReadOnlyList<Goods> Search(Func<Goods, bool> predicate)
{
    ArgumentNullException.ThrowIfNull(predicate);
    return _store.List().Where(predicate).ToList().AsReadOnly();
}
```

«Func<Goods, bool> — функція, яка отримує товар і відповідає true або false. У Search я передаю умову. Метод залишає товари, для яких умова істинна».

У CLI виконується:

```csharp
service.Search(item => item.Unit == "м" && item.Quantity >= 60);
```

Цей пошук показується в кожному звичайному запуску, окремої команди не потрібно. `item => ...` — лямбда, тобто короткий запис функції.

### 3. Фабрика сховищ

```bash
dotnet run --project src/Cli -f net10.0 --no-build -- --factory
dotnet run --project src/Cli -f net10.0 --no-build -- --file --path data/catalog.json --cache --factory
```

«Без прапорця Program.cs сам створює сховище через тернарний оператор. Із --factory він викликає StoreFactory.Create(args). Фабрика переносить створення в окремий клас, але сервіс не змінюється. Вона розташована в Cli, бо вибір конкретних залежностей належить точці входу».

Основний варіант з конкретними класами в Program.cs збережено для демонстрації. StoreFactory — альтернативна частина composition root для додаткового завдання. Це не DI-контейнер.

## Перевірки

```bash
dotnet run --project tests/ServiceChecks -f net10.0 --no-build
dotnet run --project tests/DomainChecks -f net10.0 --no-build
```

ServiceChecks: **45 passed, 0 failed** на Windows. DomainChecks: **56 passed, 0 failed**. Перевірка блокування файлу специфічна для Windows; на інших ОС її пропущено, тому нових перевірок буде 44. Це консольні перевірочні проєкти, тому команда — `dotnet run`, а не `dotnet test`.

Program.cs у Cli запускає демонстрацію, Program.cs у ServiceChecks — перевірки сервісів, Program.cs у DomainChecks — перевірки домену. Це окремі виконувані проєкти, конфлікту точок входу немає.

## Теорія: відповіді на всі 10 питань методички

1. **Composition root** — місце, де створюються й з'єднуються об'єкти. У мене це Cli/Program.cs, а в додатковому режимі він делегує створення StoreFactory.
2. **Чому сервіс не створює сховище?** Інакше він був би прив'язаний до файла. Для переходу на БД довелося б змінювати сервіс; для тестів не можна було б просто передати пам'ять або тестове сховище.
3. **DIP і DI:** DIP — принцип: важлива логіка залежить від контракту. DI — спосіб надати залежність ззовні. Тут DIP забезпечує ICatalogStore, DI — передавання store у конструктор CatalogService.
4. **Чому IReadOnlyList?** Зовнішній код не повинен додавати або вилучати записи в обхід методів сховища. У мене список реально захищений AsReadOnly, а товари скопійовані, тому зміни отриманого об'єкта теж не зберігаються без Update.
5. **Що зміниться з БД?** Додам реалізацію ICatalogStore, наприклад DbCatalogStore, і підключу її в composition root/фабриці. Бізнес-операції CatalogService залишаться ті самі. Для багатокористувацької системи окремо потрібні транзакції та контроль конкурентних змін.
6. **Навіщо DTO?** Goods має приватний конструктор і бізнес-правила. DTO — простий формат запису. ToDto готує дані для JSON, FromDto відновлює сутність через фабрику з перевірками.
7. **Скільки методів в інтерфейсі?** Лише потрібні операції. Тут п'ять. Методи «на майбутнє» змушували б кожне сховище реалізовувати непотрібну поведінку. Search працює через наявний List, тому новий член контракту не потрібний.
8. **Як тестувати без диска?** Створити InMemoryCatalogStore й передати його в CatalogService. CountingStore додатково дозволяє перевірити кількість викликів.
9. **Навіщо кеш у FileCatalogStore?** Щоб не читати й не розбирати JSON на кожен Find/List. Файл читається під час першого звернення, а після змін записується оновлений список. Це локальне сховище для одного процесу, без синхронізації паралельних записів.
10. **Чи потрібний DI-контейнер?** Ні: кілька залежностей легко створити звичайним new і передати через конструктор. Microsoft.Extensions.DependencyInjection не підключений.

## Коротко про додатковий синтаксис

- `class CatalogService(ICatalogStore store)` — первинний конструктор: параметр зазначений одразу після назви класу.
- `: ICatalogStore` — клас зобов'язується реалізувати методи інтерфейсу.
- `Goods?` — метод може повернути null, якщо товар не знайдено.
- `?? throw` — якщо результат null, одразу викинути зрозумілий виняток.
- `IEnumerable<Goods>` — послідовність товарів, яку можна перебрати.
- `Dictionary<string, Goods>` — товари за ключем Id.
- `StringComparer.OrdinalIgnoreCase` — Id G-1 та g-1 вважаються однаковими.
- `Guid.NewGuid().ToString("N")` — ідентифікатор із 32 шістнадцяткових символів. Унікальність також перевіряє Add.
- `Select(item => item.ToDto())` — перетворити кожну сутність на DTO.
- `Where(predicate)` — залишити лише елементи, які відповідають умові.
- `static readonly` — спільне поле, якому не можна призначити інший об'єкт після ініціалізації. Сам об'єкт не стає автоматично незмінним.
