# Захист лабораторної 6 — Warehouse

## Початок: що сказати

«Моя тема — склад. У п'ятій лабораторній сервіс працював зі сховищем через інтерфейс. У шостій я додав подію Changed: сервіс повідомляє, що товар додано, отримано, видано або видалено. Зовнішній код вирішує, як показати повідомлення. Сам Core не друкує і не записує журнал».

## 1. Дані події

Відкрий `src/Core/Events/CatalogChangeKind.cs` та `CatalogChangedEventArgs.cs`.

«Enum містить чотири види зміни: Added, Received, Issued, Removed. EventArgs передає Id товару, вид зміни, Delta — на скільки змінилась кількість, QuantityAfter — залишок після операції, At — час зі зсувом від UTC. Властивості мають тільки get, тому дані повідомлення не змінюються після створення».

Прихід 25 після 50: Delta=+25, QuantityAfter=75. Видача 10: Delta=-10, QuantityAfter=65. Видалення товару з 3 одиницями: Delta=-3, QuantityAfter=0, бо запис уже відсутній у каталозі.

## 2. Подія та місце її виклику

Відкрий `src/Core/Services/CatalogService.cs`.

```csharp
public event EventHandler<CatalogChangedEventArgs>? Changed;
```

«EventHandler — стандартний делегат .NET: отримує sender і дані e. Знак питання дозволяє відсутність підписників. Зовнішній код може тільки підписуватись або відписуватись; підняти подію може сам CatalogService».

Покажи Receive:

```csharp
item.RegisterArrival(quantity);
_store.Update(item);
OnChanged(item, CatalogChangeKind.Received, quantity);
```

«Спочатку перевіряються правила товару, потім новий стан зберігається. Лише після цього повідомляємо. Якщо кількість від'ємна або сховище не змогло записати дані, до OnChanged виконання не дійде».

У OnChanged покажи `Changed?.Invoke(this, change)`. `?.` пропускає виклик, якщо подія null. `this` — сервіс, який виконав зміну. Remove=false також не створює події; читання й пошук не змінюють стан, тому не повідомляють.

## 3. Два підписники в CLI

Відкрий `src/Cli/Program.cs`:

```csharp
service.Changed += OnCatalogChanged;
service.Changed += counter;
```

«Перший підписник — локальний метод: він передає повідомлення в ConsoleSink і FileSink. Другий — лямбда, яка збільшує changes. Вона захоплює зовнішню змінну, тобто створює замикання. Підписка виконується один раз. Обробники синхронні й виконуються в порядку підписки: спочатку [1], потім [2]».

```csharp
EventHandler<CatalogChangedEventArgs> counter = (_, _) =>
{
    changes++;
    Console.WriteLine($"  [2] Лямбда-лічильник: {changes}");
};
```

Параметри `_` не використовуємо. Сам делегат збережений у змінній counter, щоб можна було зняти саме цю підписку.

## 4. Запуск і журнал

Усі команди — для Git Bash:

```bash
cd /c/dev/CrossApp
dotnet build CrossApp.slnx
dotnet run --project src/Cli -f net10.0 --no-build
echo $?
tail -n 5 src/Cli/bin/Debug/net10.0/logs/app.log
```

«Додаю товар із 50 одиницями, отримую 25, видаю 10. Залишок 65. Додаю й видаляю тимчасовий товар для показу Removed. Разом п'ять подій, кожна з одним рядком у журналі. Позначки [1], [2] показують порядок обробників».

Журнал лежить біля виконуваного файлу: `Path.Combine(AppContext.BaseDirectory, "logs", "app.log")`. FileSink сам створює директорію через Directory.CreateDirectory, записує UTF-8 і дописує рядки. Тому показуємо tail, а не очікуємо рівно 5 рядків за весь час. Повний шлях виводиться в консолі. Для net8.0 заміни net10.0 у команді та шляху.

## 5. Відмови й відписка

«Від'ємний прихід, відсутній id і видача понад залишок дають зрозумілі помилки. Нових подій нуль, залишок 65. Повторне видалення дає false, теж без події».

Покажи `service.Changed -= OnCatalogChanged`.

«Знімаю перший обробник і додаю ще 5. Дані змінилися: залишок 70. Лямбда досі працює: changes=6. Але першого повідомлення й нового рядка app.log немає. Потім відписую counter, видаю 1: залишок 69, лічильник лишається 6. Це показує, що операція працює навіть без підписників».

Вивід самого CLI про залишок — пояснення демонстрації, а не рядок події. Відписки повторюються в finally, щоб завершити їх і при винятку.

## 6. Func для пошуку

```csharp
service.FindAll(p => p.Quantity < 10);
```

«Func<Goods, bool> отримує товар і повертає true, якщо він підходить. Лямбда задає критерій ззовні: залишок менший 10. Where фільтрує, ToList створює список, AsReadOnly забороняє змінювати його структуру. Це запит, від якого потрібен результат; подія потрібна для повідомлення, тому пошук зроблено методом із Func».

У звичайному режимі видно захисні окуляри з нульовим залишком. У файловому режимі можуть бути інші результати або порожній список.

## Додаткове 1. Інтерфейс сповіщень і ручний DI

Покажи `src/Core/Abstractions/INotificationSink.cs`, `src/Cli/Notifications/ConsoleSink.cs`, `FileSink.cs` та метод DemonstrateSinks у Program.

```csharp
public interface INotificationSink
{
    void Notify(CatalogChangedEventArgs change);
}

var service = new CatalogService(new InMemoryCatalogStore(), sink);
```

«Інтерфейс — договір, що одержувач уміє прийняти повідомлення. ConsoleSink друкує його, FileSink записує у файл. Cli створює конкретний об'єкт і передає сервісу через конструктор — це ручний DI. Core знає лише інтерфейс».

«Додаткова демонстрація по черзі створює сервіс із кожним sink. Підписок Changed у цих сервісів немає, але повідомлення надходять через Notify. Для кожного виконуються чотири операції. Файловий варіант записує окремий sink.log, щоб не змішувати його з демонстрацією відписки».

```bash
tail -n 4 src/Cli/bin/Debug/net10.0/logs/sink.log
```

Порівняння для відповіді: «Event дає нуль або багато підписників і керування += / -= після створення. Sink — явна залежність у конструкторі. Обидва варіанти відділяють сервіс від способу виводу. Якщо мені треба динамічно підключати різних слухачів, подія зручніша. Якщо потрібен один визначений одержувач, інтерфейс у конструкторі простіший».

Якщо запитають про помилку журналу: «FileSink перехоплює очікувані помилки IO всередині оброблення, повідомляє в stderr і збільшує FailureCount. Наступний підписник продовжує роботу. CLI повертає 1, щоб збій не був прихований. Зміна товару вже збережена й не відкочується».

## Додаткове 2. Action для пропущених рядків

Покажи `src/Core/Import/GoodsCsvImporter.cs`, метод DemonstrateImport і `data/lab06.csv`.

```csharp
public static ImportResult<GoodsDto> Load(
    string path, Action<string>? onSkipped = null)
```

У гілці ParseFailed:

```csharp
errors.Add(error);
onSkipped?.Invoke(error);
```

«Action<string> отримує текст і нічого не повертає. Для кожного пошкодженого рядка я додаю помилку до результату й викликаю передану дію. Cli передає лямбду, яка друкує повідомлення та збільшує skipped. Імпортер не знає про Console. Якщо дію не передати, імпорт працює як раніше».

На екрані: **3 DTO, 3 помилки, 3 виклики Action**. Фізичні рядки помилок: 5, 6, 7. Заголовок, коментарі та порожні рядки не є пошкодженими. Кожна помилка залишається в ImportResult.Errors незалежно від наявності callback. Callback повідомляє про помилки CSV-парсера, а доменні правила перевіряються окремо при мапінгу.

## Відповіді на всі 10 питань методички

1. **Event і поле-делегат.** До event ззовні можна тільки додавати й прибирати обробники. Публічне поле-делегат можна було б перезаписати, обнулити чи викликати ззовні. Event залишає право сповіщати у видавця.
2. **Action, Func, event.** Action — виконати передану дію без результату; Func — обчислити й повернути результат; event — повідомити підписників про факт. У нас це звіт імпорту, критерій пошуку та зміни товарів.
3. **Навіщо ?.Invoke?** Без підписників Changed=null. Умовний виклик просто пропускає повідомлення замість NullReferenceException.
4. **Один обробник кинув виняток.** Звичайний event викликає обробники послідовно. Необроблений виняток зупиняє наступних і виходить до викликача. Зміна стану вже відбулася. Тому FileSink обробляє власні помилки всередині.
5. **Чому після зміни?** Подія означає факт, що вже відбувся. До перевірок і запису можна було б повідомити про операцію, яка потім не виконається.
6. **Що таке замикання?** Функція використовує змінні зовнішньої області. Лямбда counter захоплює changes і змінює ту саму змінну; лямбда імпорту захоплює skipped.
7. **Чому нова лямбда у -= не знімає підписку?** Окремо написана лямбда не посилається на той самий обробник. Треба зберегти початковий делегат у змінній і передати його в -= або використати іменований метод.
8. **Навіщо sender?** Він показує об'єкт-видавець; тут this, тобто CatalogService. Обробники CLI його не потребують, а тест перевіряє правильний екземпляр. Один обробник міг би слухати декілька сервісів і розрізняти їх через sender.
9. **Де витік пам'яті?** Довгоживучий видавець тримає посилання на делегат, а той — на об'єкт або захоплені змінні. Без відписки короткоживучий об'єкт може не звільнитись. У короткому консольному запуску життя об'єктів зазвичай обмежене процесом, але finally та -= усе одно правильні.
10. **Чому не друкувати або логувати прямо в Core?** По-перше, кожен новий клієнт на кшталт API чи Blazor вимагав би змін бізнес-коду. По-друге, тести були б прив'язані до консолі/файлів. Подія дозволяє тестувати саме факт зміни без цих залежностей. Впроваджений INotificationSink теж відділяє реалізацію IO, але додає явну залежність від контракту сповіщень.

## Додаткове теоретичне питання: async void

«EventHandler повертає void. Якщо передати async-лямбду з await, вона стає async void, а не Task. Видавець не може await-нути її завершення. Після першого незавершеного await наступні підписники можуть продовжити роботу до завершення першого. Виняток після await не повертається звичайним способом у try/catch навколо виклику події; потрібне оброблення всередині async-обробника. Коли важливо дочекатися всіх операцій, варто проєктувати окремий Task-метод або контракт на кшталт Func<..., Task>. У цій лабораторній обробники синхронні».
