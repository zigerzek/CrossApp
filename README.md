# CrossApp — лабораторна робота 4

Доменна модель складу: сутності, інваріанти, інкапсуляція. Реалізовано основну частину та всі три додаткові завдання. Звичайний запуск показує лише демонстрацію лабораторної 4.

## Запуск і перевірка

Виконувати з кореня репозиторію:

```powershell
dotnet build CrossApp.slnx
dotnet run --project src/Cli -f net10.0 --no-build
dotnet run --project tests/DomainChecks -f net10.0 --no-build
```

Власний CSV для перевірки доменних інваріантів:

```powershell
dotnet run --project src/Cli -f net10.0 --no-build -- data/lab04.csv
```

Обидва застосунки мають цільові платформи net8.0 і net10.0, тому `-f` обов'язковий. Збірку перевірено для обох платформ; 56 автоматичних перевірок і CLI виконано на .NET 10. Для запуску з `-f net8.0` потрібен .NET 8 Runtime, якого на перевіреному комп'ютері немає. DomainChecks — самостійний перевірочний застосунок без сторонніх пакетів, запускати його через `dotnet run`, а не `dotnet test`.

## Сутності та зв'язок

- `Goods` — товар зі стабільним Id, SKU, назвою, одиницею вимірювання, залишком і необов'язковою приміткою. Залишок змінюють `RegisterArrival(int)`, `Issue(int)` і `RegisterArrival(Batch)`.
- `Batch` — партія конкретного товару. `Batch.GoodsId` має збігатися з `Goods.Id`, щоб партію можна було оприбуткувати. Кількість партії додатна й незмінна.
- `BatchStatus` — `Draft`, `Received`, `Cancelled`. Для чернетки `ReceivedDate` є запланованою датою надходження; дата передається явно й не залежить від поточного часу.

Обидві сутності мають приватні конструктори, фабрики Create, властивості без публічних set, ToDto/FromDto. DTO лишаються форматом передавання даних. Goods.FromDto викликає Create; Batch.FromDto викликає Create, перевіряє назву стану та відновлює збережений стан без повторного зарахування залишку.

## Інваріанти

- Id, SKU, назва й одиниця вимірювання товару не можуть бути null, порожніми або складатися лише з пробілів (`ArgumentException`, `Goods.Create`).
- Початковий залишок невід'ємний (`ArgumentOutOfRangeException`, `Goods.Create`).
- Кількість приходу та видачі більша за нуль (`ArgumentOutOfRangeException`, `RegisterArrival` / `Issue`).
- Не можна видати більше, ніж є на складі (`InvalidOperationException`, `Issue`).
- Прихід не може переповнити int: залишок не перевищує `int.MaxValue` (`InvalidOperationException`, `ValidateArrival`).
- Id партії та GoodsId обов'язкові (`ArgumentException`, `Batch.Create`).
- Кількість партії додатна; дата не дорівнює незаданому `default(DateOnly)` (`ArgumentOutOfRangeException`, `Batch.Create`).
- Партія має належати товару, який її приймає (`InvalidOperationException`, `Goods.RegisterArrival(Batch)`).
- Дозволено лише `Draft → Received` і `Draft → Cancelled`; повторні та зворотні переходи заборонені (`InvalidOperationException`, `Batch.NextStatus`).
- DTO не обходить перевірки: некоректні дані відхиляються фабриками; невідомий/числовий рядок статусу відхиляється (`ArgumentException`, `Batch.FromDto`).
- Null замість DTO або партії відхиляється (`ArgumentNullException`).

Усі перевірки виконуються до зміни стану. Наприклад, переповнення при оприбуткуванні залишає незмінними і залишок товару, і Draft-стан партії. Domain не використовує Console, File або Cli.

## Усі додаткові завдання

### 1. Імпорт у доменну модель з помилками

`GoodsDomainMapper.Map(ImportResult<GoodsDto>)` повертає `ImportResult<Goods>`: успішні сутності та попередні помилки розбору разом із новими порушеннями доменних інваріантів. Для кожного DTO викликається Goods.FromDto.

В ImportResult додано необов'язковий SourceLineNumbers. CSV-імпортер зберігає фізичний номер кожного успішного запису. Тому порожні рядки, коментарі й попередні помилки не зсувають номери доменних помилок. Для джерела без цих метаданих повідомлення чесно називає номер запису, а не рядка файлу.

`data/lab04.csv`: 2 коректні сутності; рядок 6 — помилка формату кількості, рядок 3 — порожній Id, рядок 5 — порожня одиниця. Помилки повертаються за етапами: спочатку помилки парсера, потім домену. Списки повертаються через AsReadOnly: приведення до IList не дозволяє Clear/Add.

### 2. Інваріант між двома сутностями

`Goods.RegisterArrival(Batch)` перевіряє відповідність GoodsId, стан партії та місткість залишку. Лише після перевірок партія стає Received, а кількість додається до товару. Відмова не змінює жодної сутності.

У цій роботі координація зосереджена в одному доменному методі. У застосунку зі сховищем таку операцію зазвичай координує сервіс: він завантажує обидві сутності, перевіряє їхню актуальність та унікальність і зберігає зміни в одній транзакції. Окрема сутність не повинна знати про базу даних. Поточна реалізація працює з об'єктами в одному потоці; вона не замінює транзакції та контроль повторних Id у майбутньому сховищі.

### 3. Enum і switch expression

```csharp
private BatchStatus NextStatus(BatchStatus target) => (_status, target) switch
{
    (BatchStatus.Draft, BatchStatus.Received) => BatchStatus.Received,
    (BatchStatus.Draft, BatchStatus.Cancelled) => BatchStatus.Cancelled,
    _ => throw new InvalidOperationException(
        $"Партія {Id}: перехід {_status} → {target} заборонений")
};
```

`Cancel()` доступний клієнту, а оприбуткування виконується через Goods. Відновлення Received/Cancelled через FromDto відтворює збережений стан і не є бізнес-переходом чи повторним приходом.

## Демонстрація

1. Успіх: 100 → прихід 50 → 150 → видача 30 → 120.
2. Відмови: перевитрата, порожній SKU, від'ємний залишок, недодатна кількість операції, порожня одиниця. Після відмов залишок 120, порівняння DTO дає True.
3. Мапінг: товар і партія відновлюються з DTO без втрати даних; некоректний DTO відхиляється.
4. Партія 20 одиниць: Draft → Received, залишок 120 → 140. Повторне оприбуткування, чужа партія та недозволені переходи відхиляються; стан збережений.
5. Імпорт lab04.csv: 2 сутності, 3 помилки з фізичними номерами рядків.

Очікувані відмови перехоплюються; виводяться тип і Message, без stack trace. Невиникнення очікуваного винятку або неправильний тип дають код виходу 1. Помилка читання CSV також дає код 1. Завершена демонстрація, включно з очікуваними неправильними даними, — код 0.

## Перевірки

DomainChecks перевіряє фабрики, null/порожні аргументи, граничні кількості, відсутність публічних конструкторів/сетерів, усі доступні переходи стану, DTO для кожного стану, переповнення, незмінність обох сутностей після відмов, точність номерів рядків і захист колекцій.

Окремо на тимчасовому проєкті підтверджено:

```csharp
goods.Quantity = -5; // CS0200: властивість лише для читання
new Goods("G", "SKU", "Назва", "шт", 0, null); // CS1729: немає доступного конструктора
```

Ці некоректні рядки навмисно не включено до основного рішення. На захисті можна тимчасово додати перший у Program.cs після створення goods, виконати build, показати CS0200, а потім прибрати рядок і повторити build.
